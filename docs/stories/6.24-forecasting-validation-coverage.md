## Sub-Story 6.24.1: Year-Value Data Corruption Filter

### Overview

| Field | Value |
|-------|-------|
| **Status:** | Ready for Development |
| **Priority:** | P0 (Critical Path) |
| **Effort:** | 1 hour |

### Problem

The PostgreSQL table extraction is capturing year column headers (2021, 2022, 2023, 2024) as metric values. This corrupts:
- **Frequency Ratio (Capacity Utilization):** Max value 2024.00 (clearly a year, not a percentage)
- **Thermal Energy:** Extreme variance from -764 to 0

### Implementation

**File:** `raglite/forecasting/timeseries_extract.py`

**Changes Required:**

1. **Add Year-Value Filter in SQL Extraction (Lines ~1824-1850):**
```python
# After extracting value, before creating TimeSeriesPoint
# Filter year values (2000-2099) that were accidentally captured as metrics
if value is not None and 2000 <= value <= 2099:
    logger.warning(f"Filtered year-like value: {value} for metric {metric}")
    continue
```

2. **Enhance Percentage Metric Validation (Lines ~2156-2191):**
```python
# For percentage metrics, also reject year-like values before clamping
if 2000 <= value <= 2099:
    logger.warning(f"Rejected year value {value} for percentage metric {metric}")
    continue
```

3. **Verify Outlier Detection for Cost Metrics:**
- Check line ~2193-2230 for cost metric `abs()` transformation
- Ensure outlier detection runs AFTER `abs()` transformation

### Acceptance Criteria

- [ ] AC1: Filter values in range 2000-2099 from Capacity Utilization (Frequency Ratio)

## Sub-Story 6.24.4: External Metrics Standalone Validation

### Overview

| Field | Value |
|-------|-------|
| **Status:** | Ready for Development |
| **Priority:** | P0 (Blocks validation of 10 external metrics) |
| **Effort:** | 2-3 hours |

### Problem

External metrics added in Sub-story 6.24.2 cannot be validated as standalone variables because:

1. **Missing extraction logic**: `extract_external_timeseries()` only supports 3 metrics (ttf_gas, petcoke, co2_eua)
2. **Hardcoded mappings**: `EXTERNAL_SOURCE_MAPPINGS` dictionary doesn't include the 10 new external metrics
3. **Architecture mismatch**: New metrics are implemented as regressors (fetched via `fetch_single_regressor()`) but validation expects database extraction

**Current Status:**
- ✅ 3 external metrics work (ttf_gas_price, petcoke_price, co2_eua_price)
- ❌ 10 new external metrics fail with "No external source mapping" error

### Root Cause Analysis

The validation flow is:
```
validate()
  → is_external = config.is_external_only
  → extract_external_timeseries(metric_name)
    → check EXTERNAL_SOURCE_MAPPINGS
      → NOT FOUND for new metrics → return None
```

But regressor fetch logic already exists:
```
fetch_single_regressor("euribor_3m")
  → ECBClient().fetch_euribor() ✅ WORKS
```

### Solution

**Option A: Extend EXTERNAL_SOURCE_MAPPINGS** (Recommended)
Create wrapper logic that uses `fetch_single_regressor()` for external-only metrics.

**Option B: Ingestion-based**
Ingest all external metrics into `external_data_points` table (requires new ingestion jobs).

**Recommendation:** Option A is faster and leverages existing regressor fetch infrastructure.

### Implementation

**File 1:** `raglite/forecasting/timeseries_extract.py`

**Add new function after `extract_external_timeseries()`:**

```python
async def extract_external_regressor_timeseries(
    metric: str,
    min_points: int = 6,
) -> TimeSeriesData | None:
    """Extract external regressor as standalone time series for validation.

    Story 6.24.4: Enables validation of external-only metrics by reusing
    regressor fetch logic. This bridges the gap between regressor system
    and validation system.

    Args:
        metric: Regressor name (e.g., "euribor_3m", "diesel", "gdp_growth")
        min_points: Minimum data points required (default 6)

    Returns:
        TimeSeriesData with points, or None if insufficient data
    """
    from datetime import datetime, timedelta
    from raglite.forecasting.regressor_fetch import fetch_single_regressor
    from raglite.shared.models import TimeSeriesData, TimeSeriesPoint

    try:
        # Fetch last 5 years of data (sufficient for forecasting validation)
        end_date = datetime.now().date()
        start_date = end_date - timedelta(days=365 * 5)

        logger.info(
            f"Fetching external regressor as time series: {metric}",
            extra={"metric": metric, "start_date": start_date, "end_date": end_date}
        )

        # Use regressor fetch infrastructure
        series = await fetch_single_regressor(metric, start_date, end_date)

        if series is None or len(series) < min_points:
            logger.warning(
                f"Insufficient data for external metric: {metric}",
                extra={"metric": metric, "points": len(series) if series is not None else 0}
            )
            return None

        # Convert pandas Series to TimeSeriesData
        points = [
            TimeSeriesPoint(
                date=idx.to_pydatetime(),
                value=float(val),
                label=f"{metric}_{idx.strftime('%Y-%m')}"
            )
            for idx, val in series.items()
        ]

        logger.info(
            f"Extracted {len(points)} points for {metric}",
            extra={"metric": metric, "points": len(points)}
        )

        return TimeSeriesData(points=points, metric_name=metric)

    except Exception as e:
        logger.error(
            f"Failed to extract external regressor time series: {metric}",
            extra={"metric": metric, "error": str(e)}
        )
        return None
```

### Lessons Learned

1. **Gap Detection Collateral Damage**
   - Metric-specific overrides needed when "gaps" are expected reporting cycles
   - Thermal Energy's quarterly pattern broke from generic EBITDA fix

2. **Correlation Assessment Can Become Outdated**
   - CO2 regressors disabled based on pre-2022 assessment
   - 2022 energy crisis changed correlation from <0.5 to 0.7-0.9
   - Re-validate after major market events

3. **Model Selection Matters for Data Type**
   - Prophet: Trending, seasonal data (sales, prices, volumes)
   - ARIMA: Stationary, mean-reverting data (sentiment, balances)
   - Regime-switching: Policy-driven structural breaks (interest rates)

4. **Data Frequency Alignment Critical**
   - GDP quarterly→monthly interpolation creates artificial smoothness
   - Keep native frequency or use proper disaggregation (Chow-Lin)
