## Problem Statement

### Current State: 4-5 Hours for 10 PDFs

The current ingestion pipeline takes **4-5 hours** to ingest 10 financial PDFs (~160 pages each). This is **10x slower than acceptable** for a production system.

**Measured Breakdown (per 160-page document):**

| Phase | Duration | Bottleneck |
|-------|----------|------------|
| Docling PDF Parsing (ACCURATE mode) | 10-15 min | CPU-bound, synchronous |
| Table Extraction + Unit Inference | 5-8 min | **200+ API calls** to Mistral |
| Chunk Metadata Extraction | 3-5 min | **400+ API calls** to Mistral |
| Embedding Generation | 1-2 min | CPU-bound (Fin-E5) |
| Storage (Qdrant + PostgreSQL) | 1-2 min | Batch I/O |
| **TOTAL PER DOCUMENT** | **25-30 min** | |
| **10 DOCUMENTS (SERIAL)** | **4-5 hours** | |

### Root Cause Analysis

**Problem 1: Serial Document Processing**
- Documents processed one at a time
- No parallelization at document level
- Underutilizes multi-core CPU (M1/M2 Macs have 8-10 cores)

**Problem 2: Excessive API Calls at Ingestion (The REAL Bottleneck)**

| Operation | Calls Per Doc | Current Concurrency | Wait Time |
|-----------|--------------|---------------------|-----------|
| Chunk Metadata Extraction | 400 | 5 (semaphore) | 400x2s/5 = 160s |
| Unit Inference (per table row) | 200-250 batches | 10 (semaphore) | 250x10s/10 = 250s |
| **TOTAL API WAIT** | | | **~7 min/doc** |

**Problem 3: No Rule-Based Pre-Filtering for Units**
- Every row with `unit=None` triggers an API call
- But 80%+ of units are predictable: EUR, %, EUR/ton, kton, Mton
- A simple regex could avoid 80% of API calls

**Problem 4: No Cross-Document Caching**
- Unit inference cache is per-table only
- Same metric ("EBITDA", "Revenue") across 10 documents = 10x redundant inference

**Problem 5: Chunk Metadata Provides Marginal Value at Ingestion**
- Metadata extraction at ingestion provides soft boosting only
- Query-time metadata extraction already exists for the QUERY itself
- Moving to lazy evaluation saves 400 API calls per document

---

## Solution: Strategy C - Query-Time Enrichment

**Key Insight:** Instead of extracting metadata for ALL 400 chunks at ingestion, extract metadata only for the 5-10 top-K results returned at query time.

**Best Practice Sources:**
- AWS RAG Best Practices: "Tiered approach - static metadata at ingestion, dynamic filtering at query time"
- Perplexity Research: "Query-time extraction is more effective for handling diverse queries"
- RAG Optimization Papers: "Lazy evaluation reduces initial processing costs by 80%+"

## Architecture Changes

### Current Flow (4-5 hours for 10 PDFs)
```
PDF -> Docling Parse -> Chunking -> [BOTTLENECK: 400 LLM calls for metadata]
    -> [BOTTLENECK: 200+ LLM calls for unit inference] -> Embeddings -> Storage
```

### New Flow (30-45 minutes for 10 PDFs)
```
PDF -> Docling Parse (parallel 2x) -> Chunking -> [SKIP metadata]
    -> [Rule-based units + LLM for tables only] -> Embeddings -> Storage

Query Time: Top-K results -> Enrich with metadata on-demand (2-3 sec budget)
```

### Architecture Patterns and Constraints

**Parallel Processing Pattern:**
- Use `asyncio.Semaphore` for controlled concurrency (matches existing codebase pattern)
- Memory budget: 8GB max for M1 Mac development = 2 concurrent 160-page PDFs
- Error isolation: Each document in its own try/except, aggregate failures

**Lazy Evaluation Pattern (Strategy C):**
- Skip expensive operations at ingestion time
- Perform enrichment on-demand at query time with timeout
- Graceful degradation: Results without metadata still useful

**Caching Pattern:**
- Global cache dict passed as parameter (no Redis until Epic 5)
- Cache key: normalized metric name (lowercase, stripped)
- Cache invalidation: Per-batch only (cleared between batch runs)
